# P1 (native memory-bounded quantized LoRA trainer) — status

This is a status note for P1, in the same spirit as
`XLOAD_UPGRADE_IMPLEMENTATION_REPORT.md`'s P0 report: say exactly what's
proven, what isn't, and what the next concrete steps are — not a claim
that P1 is done. Per the TZ's own ordering, P1 starts only after P0 is
complete (it is — see the P0 report and PR #1) and is explicitly staged:
Stage 1 (one `Linear` layer, numeric proof) before Stage 2 (one
transformer block, then a real small model) before any Android/JNI
integration, memory measurement, or acceleration work.

## What exists: Stage 1 only

`native/p1_quantized_lora/` — a **standalone** C++ proof that one
quantized (GGML Q4_0) `Linear` layer with a LoRA delta computes the
correct forward pass and the correct gradients:

```
Y = X @ dequant(Wq)^T + (alpha/rank) * (X @ A^T) @ B^T
```

with `Wq` frozen (no gradient) and `X`/`A`/`B` trainable — the same
formula `xload_trainer.py`'s NumPy/Python `_inject_lora`/`LoRALinear` path
already implements, just not yet fused with quantized storage there.

See `native/p1_quantized_lora/README.md` for exactly what's verified and
against what (independent NumPy reference + a finite-difference check
computed entirely inside the C++ binary, plus a dedicated `half_to_float`
test and a clean AddressSanitizer/UndefinedBehaviorSanitizer run). In
short: **the math and the indexing are right**, checked two independent
ways, for Q4_0 specifically, for a single Linear layer, on the host CPU,
in double precision.

Wired into CI (`.github/workflows/build.yml`): fixtures are regenerated
and the test binary is built and run with the host compiler, no NDK
needed, before the Android build steps.

## What this explicitly does NOT prove yet

Being specific here matters more than the "done" list — this is exactly
the kind of claim the TZ warns against inflating:

- **Not integrated with Android at all.** No `CMakeLists.txt` hook from
  `app/build.gradle.kts`, no JNI bridge, no `TrainingEngine` implementation
  that uses this. `TermuxTrainEngine` (the NumPy/Python path) is still the
  only real training path in the app.
- **Not a transformer block, let alone a model.** One `Linear` layer in
  isolation. No attention, no RoPE/GQA, no MLP/SwiGLU, no residual/norm
  stack.
- **Not tested against a real GGUF file.** The quantized weights are
  synthetic (random, generated by `generate_fixtures.py`), not read from
  an actual model file — no `GGUFReader`/offset-mapping/mmap code exists
  in the native module yet.
- **Not memory-measured.** No tile cache, no budget planner, no PSS/RSS
  measurement — the TZ's whole "P1 only counts as an improvement if
  memory is objectively lower than the P0 baseline" criterion is
  unevaluated; there's nothing yet to measure memory *of*.
- **Not accelerated.** Plain triple-nested loops, double precision, no
  SIMD/NEON, no fused quantized-matmul kernel, no Vulkan/NPU — performance
  was explicitly not the goal of Stage 1.
- **Only one quantization format (Q4_0), one tiny synthetic shape range.**
  Q4_K_M, Q8_0, F16 — all still unimplemented. GQA (different in/out
  widths for q_proj vs k_proj/v_proj), Gemma-3's QK-norm, Phi-3's fused
  tensors — none of that's been touched by the native code.

## Concrete next steps (in TZ order)

1. **Stage 2a**: implement one full transformer block in the same
   standalone style (attention with GQA + RoPE, SwiGLU MLP, residual/norm)
   reusing `quantized_linear_lora_forward`/`backward` for each of its
   Linear layers, verified the same two ways (independent reference +
   in-binary finite-difference), still host-only, still synthetic weights.
2. **Stage 2b**: once 1 is green, load a real small GGUF (e.g.
   Qwen2.5-0.5B Q4_0) via a minimal native GGUF reader (or by exporting
   tensors from the existing Python `GGUFReader` path for now, to decouple
   "write a native GGUF parser" from "prove the block forward/backward is
   right against a real model") and compare its output logits against
   `gguf_llama_family_model.py`'s existing NumPy path on the same input.
3. **Android/NDK integration**: add `externalNativeBuild`/CMake wiring to
   `app/build.gradle.kts`, a JNI bridge, and a new `TrainingEngine`
   implementation (name TBD after this exists) that Kotlin can select
   instead of `TermuxTrainEngine` — only after 1–2 are proven, per the
   TZ's explicit "don't substitute a forward-only prototype for a real
   native trainer" warning.
4. **Memory-bounded loading + measurement**: offset-based reads instead of
   loading a whole dequantized tensor, a bounded tile cache with a
   measurable limit, and real PSS/RSS comparison against the P0 NumPy
   baseline at equal rank/seq/dataset on one device — the TZ's actual P1
   acceptance bar, not reachable before 1–3 exist.
5. **More quantization formats + architectures**: Q4_K_M/Q8_0/F16, then
   GQA width handling, Gemma-3 QK-norm, Phi-3's fused tensors — after the
   dense Q4_0 path above is proven end to end, not in parallel with it.

No device or NDK toolchain was available in this sandbox for steps 2b-4;
they need an actual Android build environment to verify honestly rather
than being claimed from a host-only build.
