# Xload

**On-Device LoRA Trainer** — Android-приложение для локального дообучения LoRA-адаптеров
компактных LLM (0.5–3B параметров) прямо на смартфоне, без выгрузки данных в облако.

Целевые модели: Qwen2.5-0.5B/1.5B, Gemma-3-1B, Llama-3.2-1B, Phi-3-mini (в 4-bit квантизации).

## Статус проекта

Инфраструктура (Этап 1) готова, и в `:app` подключён настоящий бэкенд обучения —
[termux-train](https://pypi.org/project/termux-train/) через Chaquopy — который умеет
обучать LoRA-адаптер **на реально загруженных весах** GGUF-файла (архитектуры **qwen2**,
**llama** и **phi3**), автоматически на ускоренном NumPy-бэкенде, а не только на встроенной
демо-модели, генерировать текст через обученный адаптер прямо в приложении (шаг 5)
для проверки, что дообучение вообще что-то поменяло, и строить из примеров
датасета свободный текстовый «портрет личности» — первый шаг в сторону идеи ФБД.
Подробности и что это означает на практике — ниже.

Реализовано:

- Полный каркас Android-приложения на Kotlin + Jetpack Compose, разбитый на модули
  `:core` (чистая Kotlin/JVM логика, без зависимости от Android SDK) и `:app` (UI + бэкенд).
- Мастер из 5 экранов по стадиям пайплайна из плана: выбор модели → датасет →
  гиперпараметры → обучение → тест/экспорт.
- `:core`: валидация конфигурации, парсер JSONL-датасетов, интерфейсы `TrainingEngine` и
  `InferenceEngine` (точки подключения бэкендов) и `ReferenceLoraEngine` — независимая от
  Android справочная реализация LoRA-обновления на чистом Kotlin (21 тест, `./gradlew :core:test`).
- `:app` → `TermuxTrainEngine`: реальное обучение через termux-train — настоящий
  backprop через их autograd-движок, настоящий SafeTensors-чекпоинт, который их же
  загрузчик может прочитать обратно, **реальная загрузка весов** из импортированного
  GGUF-файла (qwen2/llama/phi3 — см. «Реальные веса»), и автоматическое ~100-кратное
  ускорение через NumPy (см. «Скорость: NumPy-бэкенд»).
- `:app` → `TermuxInferenceEngine`: чат на шаге 5 — генерация текста через тот же
  termux-train поверх обученного (или базового, если чекпоинта ещё нет) адаптера
  (см. «Инференс: чат для проверки адаптера»), и там же — «Портрет личности» —
  первый маленький шаг в сторону идеи ФБД, свободный текстовый портрет по
  примерам датасета, подмешиваемый в контекст чата (см. «Портрет личности»).
- Импорт файлов модели/датасета через Storage Access Framework — приложение не просит
  разрешение `INTERNET` и не имеет сетевых вызовов: всё офлайн, как и требует план.

### Реальные веса: GGUF → termux-train

Импортированный на первом экране GGUF-файл копируется в приватное хранилище
приложения и передаётся в Python. Если файл архитектуры **qwen2**, **llama** или
**phi3**, `app/src/main/python/gguf_llama_family_model.py` строит по его же
метаданным настоящую архитектуру на примитивах termux-train и загружает в неё
настоящие (деквантизованные) веса — вместо встроенной демо-модели `TinyTransformerLM`.
Если файл вообще не импортирован, используется демо-путь — это осознанный fallback,
не ошибка. А вот если файл **импортирован**, но не читается, его архитектура не
поддержана, или его токенизатор не gpt2-style BPE (см. про phi3 ниже) — обучение
**не** откатывается на демо-путь молча, а завершается чистым `FAILED` с понятным
сообщением (это разные ветки в `xload_trainer.py`: демо-путь — только когда
`model_path` вообще не передан; любая ошибка при попытке загрузить переданный файл
идёт в `FAILED`, а не в тихий fallback — иначе пользователь думал бы, что дообучил
именно свою модель, хотя на деле она не подгрузилась).

**Почему именно так и что для этого пришлось написать:**

- В termux-train нет ни загрузчика GGUF, ни RMSNorm, ни grouped-query attention,
  ни SwiGLU-FFN — только универсальные `LayerNorm`/`MultiHeadAttention`/`FeedForward(ReLU)`.
  Всё это (`app/src/main/python/llama_style_blocks.py`) написано вручную поверх их
  тензоров/автограда. Qwen2, Llama и Phi-3-mini делят один и тот же набор блоков —
  разница между ними чисто конфигурационная: bias на q/k/v (есть только у Qwen2) —
  параметр `qkv_bias`; а у Phi-3 ещё и **слитые** тензоры внимания/MLP (см. ниже).
- Разбор самого GGUF и **деквантизация** — не самодельные: используется официальный
  пакет [`gguf`](https://pypi.org/project/gguf/) (справочная реализация от команды
  llama.cpp, чистый Python + numpy) через `gguf.quants.dequantize()` — а не
  переизобретённая вручную математика квантизации.
- Токенизатор (`app/src/main/python/gguf_bpe.py`) — байт-уровневый BPE в стиле
  GPT2/Qwen2/Llama, построенный целиком из словаря/merges, встроенных в сам GGUF-файл
  (никакого сетевого скачивания vocab). Известное упрощение: нет regex-этапа
  предтокенизации (пунктуация/числа не выделяются в отдельные чанки перед BPE
  так, как это делает эталонный токенизатор) — обычный текст токенизируется
  корректно, для текста с обилием пунктуации возможны отличия от эталона.
- **Phi-3-mini — слитые тензоры, но те же блоки.** По `modeling_phi3.py`/
  `configuration_phi3.py` (тот же приём — установка `transformers` в изолированный
  venv ради чтения первоисточника) Phi-3 архитектурно устроен как Qwen2/Llama:
  обычная `x*weight` RMSNorm, стандартное `1/sqrt(head_dim)` масштабирование
  внимания, нигде нет bias, gate*up SwiGLU с тем же порядком половин (gate, затем
  up), что уже считает `SwiGLU.forward()` — с точностью до порядка умножения,
  которая не важна. Единственное реальное отличие: llama.cpp хранит Phi-3 attention
  и MLP как **слитые** тензоры — один `attn_qkv.weight` (Q, затем K, затем V по
  выходной оси; порядок сверен по срезам в `Phi3Attention.forward()`) и один
  `ffn_up.weight`, хранящий `gate_up_proj` (gate, затем up; сверено по
  `Phi3MLP.forward()` и по `MODEL_ARCH.PHI3` в `gguf.constants` — там действительно
  нет отдельного `FFN_GATE`-тензора). `_split_out_axis()` в
  `gguf_llama_family_model.py` разбирает каждый слитый тензор на обычные матрицы
  прямо при загрузке — сами блочные классы про слияние ничего не знают и не
  менялись.
- **Токенизатор Phi-3 — непроверенный риск, а не мелочь.** `GgufBpeTokenizer`
  реализует только gpt2-style byte-BPE (то, что реально используют Qwen2 и
  Llama-3(.2)); опубликованный токенизатор Phi-3-mini — производная от
  SentencePiece-словаря Llama-2, принципиально другой алгоритм. Это **не**
  проверено по исходнику — выбор токенизатора хранится в файлах модели, а не в коде
  архитектуры, и `huggingface.co` недоступен из песочницы. Поэтому
  `load_gguf_model()` при загрузке любого файла проверяет его собственное поле
  `tokenizer.ggml.model`: если это не `"gpt2"`, загрузка падает с понятным
  `ValueError` вместо того, чтобы молча прогнать текст через неподходящий алгоритм.
  Если настоящий Phi-3-mini GGUF действительно окажется SentencePiece-файлом,
  результат — чистый `FAILED` при импорте с этим сообщением, а не тихая порча
  датасета.

**Как проверялось** (в этой песочнице нет доступа ни к HuggingFace, ни к какому-либо
хосту с реальными весами — `huggingface.co` заблокирован политикой прокси так же,
как `dl.google.com`; скачать настоящий GGUF-файл для проверки было невозможно):

1. Синтетический GGUF-файл (сгенерирован через `gguf.GGUFWriter` с настоящими
   ключами метаданных `qwen2.*` и по-настоящему квантованным Q4_0-тензором) —
   деквантизация сверена с оригиналом до 4-битной точности (~9% относительной
   ошибки — ожидаемо для Q4_0, не баг).
2. Полный forward pass загруженной из такого файла модели сверен **с независимой
   эталонной реализацией на чистом numpy** (писалась отдельно и по-другому) —
   совпадение с точностью до ~0.3% (обычное накопление float32-погрешности через
   ~10 операций, не расхождение в логике). Первая попытка разошлась на 63% —
   оказалось, что Qwen2 (в отличие от большинства RoPE/GQA-архитектур) держит bias
   на q/k/v-проекциях, а загрузчик изначально копировал только веса. Это нашлось и
   исправлено именно через сравнение с эталоном, а не угадыванием.
3. LoRA-инъекция и один шаг обучения — поверх уже загруженной из файла модели
   (не демо-модели) — тоже прогнаны и работают, для всех трёх архитектур.
4. Все пути `xload_trainer.py` (демо, qwen2, llama, phi3, неподдержанная архитектура,
   неподдержанный тип токенизатора) прогнаны через один и тот же тестовый скрипт
   end-to-end, с реальным колбэком прогресса.
5. Для Phi-3 отдельно: та же двухшаговая проверка, что и для Qwen2/Llama (синтетический
   `phi3`-файл со слитыми `attn_qkv.weight`/`ffn_up.weight` + независимый numpy-эталон,
   который сам разбирает слияние по тому же порядку срезов) — совпадение ~0.4%,
   такое же по масштабу, как у Qwen2/Llama. Плюс отдельный тест: синтетический
   `phi3`-файл с `tokenizer.ggml.model = "llama"` (имитация SentencePiece) даёт
   чистый `FAILED` с сообщением про неподдержанный токенизатор, а не падение или
   тихая порча — то есть именно то поведение, которое обещано в ограничениях ниже.

Все эти проверки — реальные прогоны в локальном venv (`pip install termux-train==1.1.3
gguf==0.19.0 numpy`, Python 3.11), а не чтение документации. Чего по-прежнему не
было и не могло быть: сборки `:app` через Chaquopy на настоящем Android SDK/устройстве
(см. «Сборка и запуск» ниже) и проверки на **настоящем** (не синтетическом) GGUF-файле.

**Ограничения, которые стоит знать:**

- Поддержаны только архитектуры **qwen2**, **llama** и **phi3**. Gemma-3 — нет
  (см. «Что дальше», п. 1 — там же зафиксировано, что именно для неё нужно).
- Для **phi3** — только если у файла `tokenizer.ggml.model == "gpt2"`. Настоящие
  Phi-3-mini GGUF-файлы могут оказаться SentencePiece-токенизатором (не проверено —
  см. выше); в этом случае импорт корректно завершится `FAILED`, а не тихой порчей
  токенизации. Также не читаются `partial_rotary_factor`, `sliding_window` и
  long-context RoPE-масштабирование (`ROPE_FACTORS_LONG/SHORT`) — если реальный файл
  их выставляет, результат будет тихо неверным (тот же класс риска, что и не
  реализованные для Gemma-3 sliding-window/двойная RoPE-тета).
- Токенизация без regex-предтокенизации (см. выше) — не идентична эталону на
  тексте с пунктуацией/числами.
- Ничего не квантуется обратно при сохранении адаптера — сам адаптер (LoRA A/B)
  всегда float32, только веса **базовой** модели остаются в их исходном
  квантованном виде в памяти на время forward/backward.

### Скорость: NumPy-бэкенд (~100×)

termux-train сам, без единой строчки нашего кода, переключается на NumPy-бэкенд,
как только NumPy импортируется — раньше в проекте NumPy не было, но
`app/build.gradle.kts` уже ставил его как зависимость пакета `gguf`, и это
попутно включило и ускорение автограда termux-train. Замерено в локальном venv
на одном и том же forward+backward прогоне: **8.2с (чистый Python) → 0.067–0.085с
(NumPy) — то есть на два порядка быстрее**, при этом корректность не пострадала
(все проверки из раздела выше уже шли на NumPy-бэкенде). `xload_trainer.py`
теперь явно вызывает `termux_train.set_backend("numpy")` в начале `train()`
(best-effort — если почему-то не получится, обучение всё равно продолжится, просто
на бэкенде по умолчанию) — не полагаясь только на неявный автовыбор, который может
вести себя иначе на Android/Chaquopy, чем в этой Linux-песочнице.

Отдельно существует `ameva-runtime` (extra `[vulkan]` у termux-train) — **реальный**
пакет на PyPI, тоже чистый Python (`py3-none-any`), но его `vulkan/bindings.py`
похож на тонкую ctypes-обвязку над системной `libvulkan.so` устройства, а не на
бандл с нативным кодом. Это значит, что рабочий GPU-путь зависит от Vulkan-драйвера
конкретного телефона (см. риски ниже про фрагментацию Snapdragon/MediaTek/Exynos) —
то, что физически невозможно проверить без реального устройства. Пакет **не**
подключён: NumPy-бэкенд уже даёт кратный выигрыш и проверен, Vulkan — не подключён
намеренно до появления возможности протестировать на реальном железе.

### Инференс: чат для проверки адаптера

Шаг 5 (`TestExportScreen`) теперь не просто экспортирует чекпоинт — там есть чат:
ввели реплику, `app/src/main/python/xload_inference.py` (через новый
`TermuxInferenceEngine`/`InferenceEngine`, тот же Chaquopy-мост, что и обучение)
пересобирает **точно ту же** архитектуру и LoRA-обёртку, что и обучение (тот же
GGUF-файл или демо-модель, тот же rank/alpha), подгружает в неё сохранённый адаптер
и генерирует ответ токен за токеном тем же termux-train.

**Почему пересборка архитектуры обязательна, а не просто "загрузить файл":**
`termux_train.checkpoint.lora_io.load_lora_adapter()` находит LoRA-слои внутри уже
готовой Kotlin/Python-модели по пути в дереве модулей и **строго** сверяет
in_features/out_features/rank/alpha каждого слоя с тем, что сохранено в чекпоинте —
несовпадение (например, другой rank) даёт понятную ошибку, а не тихую загрузку не в тот
слой. Поэтому `TrainingConfig.lora` и `modelFilePath`, использованные при обучении,
обязаны быть теми же самыми при инференсе — `TrainingSessionViewModel` передаёт их из
своего же состояния (`loraConfig`/`importedModelFilePath`), а не переизобретает заново.
Это же строгое сравнение проверено отдельным тестом: инференс с **другим** rank, чем
использовался при обучении, даёт чистый `FAILED` с сообщением о несовпадении rank, а
не крэш или тихую порчу весов.

**Известные упрощения (сознательные, не недосмотр):**

- **Нет KV-кэша.** У `TinyTransformerLM` (демо-архитектура) он вообще-то уже есть
  (`use_cache`/`past_key_values` в её `forward()`), но у `GQAAttention`
  (`llama_style_blocks.py`, всё, что грузится из реальных GGUF-файлов) — нет: пришлось
  бы учить самописные attention-блоки конкатенировать закэшированные K/V и применять
  RoPE с произвольным `position_offset`, а проверить это можно только на реальном
  устройстве с длинной генерацией, которого нет. Вместо того чтобы дать демо-пути
  быстрый путь, которого нет у пути с реальными весами (непоследовательно и мешает
  сравнивать), генерация **везде** одинаково пересчитывает полный forward pass по всей
  последовательности на каждый новый токен — O(n²) от длины ответа, поэтому
  `maxNewTokens` жёстко ограничен (`MAX_NEW_TOKENS_CAP = 200` в Python,
  `GenerationParams` в Kotlin проверяет то же самое число), а не оставлен на усмотрение вызывающего.
- **Сэмплирование простое**: температура + top-k поверх обычного softmax — без
  repetition penalty и без nucleus (top-p) сэмплирования.
- Промпт форматируется той же функцией `_format_sample()`, что и обучающие примеры
  (`"{instruction} -> "`), чтобы дообученное поведение вообще имело шанс проявиться —
  случайный текст без этого формата модель, обученная на парах "X -> Y", скорее всего
  продолжит не так, как ожидается.

**Как проверялось** (тем же способом, что и обучение — реальные прогоны в локальном
venv, без реального устройства и без настоящих весов):

1. Полный цикл train → save adapter → **пересобрать модель с нуля** → load adapter →
   generate — прогнан для демо-модели и отдельно для синтетического GGUF-файла
   (phi3, фьюженые тензоры) — самый рискованный случай, поскольку именно он проверяет,
   что пересобранная для инференса модель архитектурно совпадает с той, что сохранила
   чекпоинт.
2. Отмена генерации на середине — гонка из отдельного потока (тот же
   `_cancelled`-паттерн, что и в `xload_trainer.py`), подтверждено, что генерация
   останавливается и эмитит `CANCELLED`, а не зависает или доедает до конца.
3. Несовпадение rank между обучением и инференсом — чистый `FAILED` с понятным
   сообщением (см. выше), не крэш.
4. Отдельно найденный и исправленный баг: `ByteTokenizer.decode()` (демо-путь) по
   умолчанию `errors="strict"` и **крэшится** `UnicodeDecodeError`, если поток байт на
   момент декодирования обрывается на середине многобайтового UTF-8 символа — а именно
   так и происходит при потоковой перегенерации после каждого нового токена. Найдено
   тестом (`assertEquals`-стиль прогон сразу упал на первом же сценарии), исправлено
   явным запросом `errors="replace"` с фолбэком на пословный вызов для
   `GgufBpeTokenizer`, у которого такого параметра нет вовсе (свой, другой сигнатурой).

### Портрет личности (пробник)

Отдельная карточка на шаге 5 (не требует завершённого обучения — достаточно
загруженного на шаге 2 датасета): кнопка «Построить портрет» прогоняет несколько
примеров датасета через ту же on-device модель (`xload_inference.py` →
`analyze_personality()`, без LoRA и без чекпоинта — описание стиля по примерам
не требует именно *дообученных* весов) с промптом «опиши стиль общения,
характерные темы и манеру принятия решений» и получает свободный текстовый
портрет. Если портрет построен, он подмешивается в каждое сообщение чата как
контекст (`"Контекст о собеседнике: {портрет}\n\nСообщение: {текст}"`).

**Это не ФБД** — контекст обсуждения важен: идея карты личности «по образу
поведения и подобию человека» зацепила именно как развитие темы фрактальной
памяти, но сам ФБД (FractalMind, RAPTOR-кластеризация) по-прежнему отложен
(см. ниже) — вопрос «где хранить и как кластеризовать по-настоящему» в этом
заходе не решался, вместо этого хотелось за один заход посмотреть на
форму фичи целиком, «PC-free», без внешнего Rust-сервера. Это первый маленький
шаг, а не аналог RAPTOR: обычная суммаризация текстом, без иерархической
кластеризации, без структурированных полей (черты/темы отдельно), без эмбеддингов
вообще — то, что обсуждалось как более амбициозная цель «на потом» (вплоть до
модели, обученной на рекурсии фракталов, а не на векторах), тоже осталось за
рамками этого захода.

**Найденный по пути баг — и он реальный, не только для портрета.** Промпт
портрета в основном на русском, а `_build_personality_prompt()` кладёт саму
инструкцию («Опиши стиль... Описание:») **в конец** промпта, а не в начало —
намеренно: `ByteTokenizer` (демо-путь) кодирует байт-в-байт без BPE-слияний,
и кириллица (2 байта на символ в UTF-8) даёт **вдвое больше токенов**, чем
кажется по длине строки — один короткий пример уже занял 370 токенов из 256
(`DEMO_MAX_SEQ_LEN`) при первой попытке. Хуже того, обрезка промпта в обеих
функциях (`generate()` и `analyze_personality()`) считалась от `max_seq_len`
целиком, а не от `max_seq_len - max_new_tokens` — то есть если сам промпт
после обрезки занимал ровно весь бюджет контекста, генерировать было уже
физически некуда (`len(ids) >= max_seq_len` истинно с первого шага), и на
выходе тихо получался пустой текст вместо ошибки. Оба нашлись прогоном теста
(не угадыванием): обрезка теперь общая — `_run_generation_loop()` сама
резервирует место под `max_new_tokens` до того, как обрезать промпт, — и
исправление задним числом улучшило и обычный чат тоже, не только портрет.

### Что нужно для Gemma-3 (исследовано, не реализовано)

Чтобы не гадать по памяти, архитектура Gemma-3 проверена по первоисточнику: пакет
`transformers` был установлен в изолированный venv именно ради чтения его
`modeling_gemma3.py`/`configuration_gemma3.py` как эталона. Оказалось, что Gemma-3
меньше похожа на Qwen2/Llama, чем казалось:

- **RMSNorm другой формулы**: `x_normed * (1.0 + weight)`, а не `x_normed * weight`
  (вес инициализируется нулями, а не единицами) — тривиальная, но обязательная замена.
- **Своё масштабирование внимания**: `query_pre_attn_scalar ** -0.5` вместо
  стандартного `1/sqrt(head_dim)` (в дефолтном конфиге оба значения совпадают
  численно, но это конфигурационное значение, а не производная от head_dim).
- **Чередование sliding-window и global attention**: каждый 6-й слой — global,
  остальные — sliding (окно по умолчанию 4096), причём у global и local слоёв
  **разный** `rope_theta` (1 000 000 против 10 000 соответственно).
- **GeGLU вместо SwiGLU** в MLP (`gelu_pytorch_tanh(gate_proj(x)) * up_proj(x)`).
- `attn_logit_softcapping`/`final_logit_softcapping` в Gemma-3 (в отличие от
  Gemma-2) по умолчанию `None` — capping можно не реализовывать.

Ничего из `llama_style_blocks.py` для этого не подходит один в один — нужен
отдельный набор блоков. Осталось вне рамок этого захода из-за объёма и того, что
проверить получившееся будет можно только через синтетический GGUF + независимый
эталон (как для Qwen2), без реального файла — с учётом количества деталей риск
тихой ошибки заметно выше, чем у Qwen2/Llama.

### FBD/фрактальная память — отложено (дважды, осознанно)

Второй присланный план (интеграция [FractalMind](https://github.com/madkoding/fractalmind) +
RAPTOR поверх той же LoRA-ветки) по-прежнему не реализован — теперь уже после того, как его
исходники (не только README) были прочитаны напрямую, чтобы разобраться в реальном облачном
риске, а не гадать по документации:

- **Эмбеддинги — реально локальные.** Дефолтный провайдер (`EmbeddingService::default()` →
  `FastEmbedProvider`, `src/embeddings/service.rs`/`fastembed_provider.rs`) — это FastEmbed,
  ONNX-модель, гоняемая прямо в Rust-процессе, без Ollama вообще. Единственная оговорка:
  `fastembed = { features = ["online"] }` в `Cargo.toml` — при первом запуске FastEmbed сам
  качает свой ONNX-файл из сети (разовая загрузка, не при каждом запросе) — README-шная
  формулировка «no external API needed!» это не совсем честно замалчивает.
- **Чат/суммаризация (REM-фаза) — вот где реальный облачный вызов**, и он именно там, где план
  и предполагал: `CHAT_PROVIDER`/`SUMMARIZER_PROVIDER=ollama-cloud` по умолчанию. Но сам
  Ollama-провайдер (`src/models/llm/providers/ollama.rs`) — просто HTTP-клиент к
  настраиваемому `OLLAMA_BASE_URL` (cloud или `http://localhost:11434` — код один и тот же,
  различие только в опциональном API-ключе). Контракт целиком вычитан из исходника:
  `POST {base}/api/chat` — `{"model", "messages":[{"role","content"}], "stream": false,
  "options": {"temperature","num_predict"}}` → `{"message": {"content"}, "done"}`;
  `POST {base}/api/embed` — `{"model","input"}` → `{"embeddings": [[...]]}` (с фолбэком на
  устаревший `/api/embeddings`); `GET {base}/api/tags` — health-check. Значит теоретически
  можно подставить вместо Ollama лёгкий HTTP-шim поверх уже работающего `xload_inference.py`
  (см. «Инференс» выше) — FractalMind при этом не меняется ни строкой.
- **Но это не главная проблема.** У FractalMind нигде — ни в README, ни в docs/, ни в
  Cargo.toml/Dockerfile — нет НИКАКОГО мобильного прицела: это Docker-first сервер
  (README прямо пишет «Minimum 4GB RAM (8GB recommended)»). Запуск самого Rust+SurrealDB+Axum
  процесса на Android (Termux либо кросс-компиляция под `aarch64-linux-android`) — отдельная,
  непроверенная инженерная задача, не имеющая отношения к тому, какой LLM он вызывает.

Дан выбор (сопутствующая машина в локальной сети / порт на сам телефон через Termux / сначала
только HTTP-шim под Ollama API, независимо от того, где будет жить сам сервер / отложить ещё
раз) — решено отложить ещё раз. ФБД возвращается в работу отдельным заходом.

## Архитектура

```
Xload/
├── core/   — чистый Kotlin/JVM модуль, без Android-зависимостей
│   └── src/main/kotlin/io/github/terminaldetector/xload/core/
│       ├── model/      — BaseModel, LoraConfig, TrainingConfig (несёт modelFilePath),
│       │                 TrainingProgress, DatasetSample, AdapterCheckpoint,
│       │                 GenerationParams, GenerationProgress
│       ├── dataset/    — JsonlDatasetParser: построчный разбор JSONL с отчётом об ошибках
│       ├── engine/     — TrainingEngine и InferenceEngine: точки подключения бэкендов
│       │   └── reference/ — ReferenceLoraEngine: справочная LoRA-математика на чистом
│       │                    Kotlin (W*x + scaling*B*A*x, SGD) — демонстрирует пайплайн
│       │                    без Python/NDK, но не языковая модель
│       └── checkpoint/ — AdapterCheckpointJson: сериализация чекпоинта ReferenceLoraEngine
│                          в JSON (свой формат, не для termux-train)
└── app/    — Android-приложение (Jetpack Compose, Material 3, Navigation Compose)
    └── src/main/
        ├── python/
        │   ├── xload_trainer.py            — точка входа для Kotlin: демо- или реальный путь
        │   ├── xload_inference.py          — чат (generate) и портрет личности
        │   │                                 (analyze_personality) поверх общего цикла генерации
        │   ├── gguf_llama_family_model.py  — сборка qwen2/llama/phi3-модели из метаданных GGUF
        │   ├── llama_style_blocks.py       — RMSNorm/SwiGLU/GQA-attention на примитивах termux-train
        │   └── gguf_bpe.py                 — BPE-токенизатор из встроенного в GGUF словаря
        └── kotlin/io/github/terminaldetector/xload/app/
            ├── engine/      — TermuxTrainEngine и TermuxInferenceEngine: Kotlin↔Python мост (Chaquopy)
            ├── ui/screens/  — 5 экранов мастера (шаг 5 несёт чат и портрет личности)
            ├── ui/theme/    — тема Material 3 (с поддержкой Dynamic Color)
            └── viewmodel/   — TrainingSessionViewModel — состояние всего мастера,
                                копирует импортированный файл в приватное хранилище
```

`TrainingEngine`/`InferenceEngine` — граница между UI и бэкендами обучения/инференса,
которую сейчас реализуют `ReferenceLoraEngine` (в `:core`, чистый Kotlin, только
обучение) и `TermuxTrainEngine`/`TermuxInferenceEngine` (в `:app`, активны по
умолчанию); MobileFineTuner/QVAC Fabric/ExecuTorch (обучение) и llama.cpp/MLC-LLM/
MediaPipe LlmInference (инференс) встанут сюда же:

```kotlin
interface TrainingEngine {
    fun train(config: TrainingConfig, dataset: List<DatasetSample>): Flow<TrainingProgress>
    fun cancel()
}

interface InferenceEngine {
    fun generate(
        lora: LoraConfig, modelFilePath: String?, checkpointPath: String,
        prompt: String, params: GenerationParams = GenerationParams(),
    ): Flow<GenerationProgress>
    fun analyzePersonality(
        dataset: List<DatasetSample>, modelFilePath: String?,
        params: GenerationParams = GenerationParams(),
    ): Flow<GenerationProgress>
    fun cancel()
}
```

## Сборка и запуск

`:core` — обычный Kotlin/JVM модуль, собирается и тестируется где угодно:

```bash
./gradlew :core:test
```

`:app` требует Android SDK, а также доступ к **Google Maven** (`dl.google.com`,
для Android Gradle Plugin и AndroidX/Compose) и к **Chaquopy Maven** (`chaquo.com`,
для плагина и Python-рантайма Android) — откройте проект в Android Studio (Koala+),
она сама подтянет SDK/AGP/Chaquopy. minSdk 30 (Android 11+), т.к. плану нужны
NNAPI/Vulkan. Ничего из этого не было доступно в изолированной среде, где писался
этот код (см. подробности выше) — `:core` и вся Python-логика (`xload_trainer.py`,
`xload_inference.py`, `gguf_llama_family_model.py`, `llama_style_blocks.py`,
`gguf_bpe.py`) реально протестированы в локальном venv, `:app` в целом — нет
(Kotlin-код для чата/инференса проверен только внимательным ручным разбором типов
и сверкой с уже работающими `TermuxTrainEngine`/`PyTrainingProgress`, не компиляцией);
при первом открытии в Android Studio возможны мелкие правки версий.

Проверить Python-логику локально (без Android) можно и так:

```bash
python3 -m venv .venv && .venv/bin/pip install termux-train==1.1.3 gguf==0.19.0 numpy
cd app/src/main/python && ../../../../.venv/bin/python3 -c "import xload_trainer"
```

## Что дальше (дорожная карта)

1. **Gemma-3** — уже исследована по исходникам `transformers` (см. выше — известно
   ровно что реализовывать: RMSNorm `*(1+weight)`, `query_pre_attn_scalar`,
   чередование sliding/global attention с двумя rope_theta, GeGLU), но не
   реализована — нужен отдельный набор блоков, риск тихой ошибки выше, чем у
   Qwen2/Llama/Phi-3 (см. выше).
2. **KV-кэш для реальных весов / настоящий инференс-движок** — сегодняшний чат (см.
   «Инференс» выше) — это termux-train без KV-кэша, годится только для короткой
   проверки. llama.cpp / MLC-LLM / MediaPipe LlmInference как отдельный
   `InferenceEngine` были бы одновременно быстрее и не нуждались бы в переносе
   KV-кэша на самописные GQAAttention-блоки.
3. **Реальный Vulkan** — `ameva-runtime[vulkan]` (см. «Скорость» выше) на реальном
   устройстве с проверкой корректности числового результата, не только скорости.
   Либо/дополнительно MobileFineTuner (NDK/C++) или QVAC Fabric (GPU) как отдельные
   `TrainingEngine`.
4. **Regex-предтокенизация** — для полного совпадения с эталонным BPE на
   пунктуации/числах (см. ограничения выше).
5. **GPU и энергоэффективность** — мониторинг температуры с паузой при перегреве.
6. **UI-полировка** — выбор целевых LoRA-модулей вручную (сейчас берутся по
   умолчанию из `BaseModel.targetModules`), сохранение прогресса/настроек между
   запусками, локализация строк через ресурсы (сейчас тексты захардкожены на русском).
7. **ФБД-ветка** (намеренно в самом конце) — FractalMind/RAPTOR, после решения
   вопроса с Ollama Cloud (локальная замена, либо явное согласие пользователя на
   этот один вызов).

## Риски (из исходного плана)

- **Память**: обучение 3B-модели может потребовать >6 ГБ ОЗУ — часть устройств отсеется.
- **Скорость**: NumPy-бэкенд уже подключён и даёт ~100× (см. выше); для реального
  ускорения младших моделей (0.5–1.5B) на слабом CPU счёт всё равно может идти на
  часы для полноценного датасета — план предупреждал именно об этом. GPU (Vulkan)
  ускорил бы дальше, но не проверен на реальном железе (см. «Что дальше», п. 3).
- **Термотроттлинг**: длительное обучение греет устройство — нужен мониторинг и паузы.
- **Фрагментация**: Snapdragon/MediaTek/Exynos по-разному поддерживают Vulkan/OpenCL.
